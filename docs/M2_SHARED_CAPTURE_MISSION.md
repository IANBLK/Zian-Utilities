# M2: shared capture missions (alpha.10)

This is an isolated Youer 1.21.1 trial. Enable only `-Dzianutilities.sharedCaptureMissionTestEnabled=true` before `-jar`; leave the older capture trial and cycle flags off. The feature does not deliver rewards or change AVECOINS balances.

The server derives **one mission definition for everyone** from each fixed three-hour window in `America/Guayaquil` (00:00, 03:00, 06:00, and so on). The definition has one stable mission ID for every player, and needs no separate per-player copy. At 00:00, 06:00, 12:00 and 18:00 the objective is **capture five Pokémon**. At 03:00, 09:00, 15:00 and 21:00 it is **capture five different species**. Both use only captures from generations active at the time, so a generation change cannot leave a species-specific requirement impossible to complete. Each real Pokémon UUID counts at most once. Neither objective grants a reward yet.

Any player, including a non-operator, can use `/zian quest shared status` to see the global offer and their own progress. The player must use `/zian quest shared accept` in each window before captures count. Acceptance is idempotent and cannot reset a completed or partial mission. Captures before acceptance are ignored. At the boundary, an accepted mission with 0/5, partial, or complete progress is moved to the player's **previous** record; the new global offer is shown as unaccepted. No progress carries forward. Players who do not accept create no files. Server restarts do not move windows or duplicate completions.

Only the current and the latest previous acceptance are retained per player under `world/data/zianutilities/quest_assignments/shared_capture_v1/`. This is at most two small files per participating player, irrespective of the number of three-hour windows. Previous test data under `capture_three_global_v1`, `capture_three_active_v1`, and `capture_any_active_v1` are untouched. The definition is derived deterministically and is not written 1,000 times.

Acceptance test: with Gen7 active, compare `/zian quest shared status` on two accounts. They should show the same mission ID and objective, both initially unaccepted. Accept on only one account and capture one valid Pokémon: that account reaches 1/5, while the other remains unaccepted. Accept on the second account and capture separately. Restart with the same JAR and flag before the boundary; both progress records and the shared ID must remain. After the natural boundary, both should see the next global objective as unaccepted; a capture before accepting it must not count. No balance should change. The exact boundary, two objective variants, restart, invalid generations, duplicates, and bounded storage are covered by core tests; Youer runtime acceptance is still required.
